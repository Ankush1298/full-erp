### 2.1 Gaps (ordered by consequence)

- **G1** No invitation or password-setup path for the first administrator; the stand-in is operator SQL. Blocks onboarding a real school without hand-edited credentials.
- **G3** No CLI command issues the MFA bootstrap ticket; an operator must call the library function. (Also no operator command to revoke or re-issue it after expiry other than calling it again.)
- **G2** Invitation does not carry the intended role/scope; the administrator must grant it separately, and an unassigned invitee sees a bare 403 with no explanation.
- **G4** No production invitation mailer (`DisabledInvitationMailer` only).
- **G5** The type does not drive anything beyond labels (no school presets, no hiding of college-only steps).

## 4. School role design (PROPOSAL, nothing implemented)

Four different things must not be confused:

- **Display label**: text shown for a role code (doc 44). No effect on access.
- **Job designation**: an HR title on the employee's posting (`designations` + `employee_postings.designation_id`, doc 20). Descriptive; it grants nothing.
- **System role**: a row of the eight codes in `role-matrix.ts`; the only thing that carries permissions, bounded by a scope (organization, campus, department) or by an assignment test.
- **Contextual assignment**: a dated relationship that makes a resource "assigned" (`faculty_assignments`, `section_class_teachers`). Evaluated by the ASSIGNED resolvers; it needs a base role that holds the permission.

| Proposed school role               | Kind                                        | Maps to                                                        | Scope / context                               | New permission?                                                                                                                                                                                                                                                                              |
| ---------------------------------- | ------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Principal                          | System role + designation                   | `COLLEGE_ADMIN`                                                | organization                                  | No. Exactly today's head-of-institution authority. A second "administrator" role would duplicate it.                                                                                |

### 4.1 Role-by-role rules

- A designation is never read by the server for access. The only way to gain authority is a role assignment, audited and within `GRANT_RULES`.
- No redundant privileged role is created: School Administrator, Admissions Officer and Vice Principal reuse existing codes.
- Smallest genuinely necessary additions: **none for the pilot's current modules**. Later: `exam.*` and `finance.*` sets when those milestones exist (new permissions, with their own role template), and, if the owner wants a class teacher to see section-wide attendance, an ASSIGNED resolver branch (no new permission).

### 4.2 Display for schools (builds on doc 44 §3.1)

Doc 44's provisional labels are consistent with this table (Principal = COLLEGE_ADMIN, Vice Principal = CAMPUS_ADMIN, Teacher = FACULTY, Admissions office = REGISTRAR). One tension: REGISTRAR is also proposed as "School Administrator", so the label "Admissions office" is too narrow; the safest label is "Registrar" with the designation carrying the job title (OD-I2).

## 8. Update: operator-only first-administrator onboarding implemented (G1, G3, S1 closed)

Status: implemented and tested on synthetic data, uncommitted. **OD-I1 remains PROPOSED**: this is the recommended mechanism built, not an owner approval of onboarding any real institution; OD-I2 to OD-I5 are untouched. No migration, no permission, no role grant and no HTTP route was added.

| Piece                           | Behaviour                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools/platform/first-admin.ts` | `issueFirstAdminInvitation`, `revokeFirstAdminInvitation`, `issueFirstAdminMfaTicket`, `assertLocalTokenOutput`. CLI commands `admin:invite`, `admin:invite-revoke`, `admin:mfa-ticket` in `tools/platform/cli.ts`. Runbook: `docs/runbooks/first-administrator-onboarding.md`.                                                                          |
| Token                           | 256-bit random, SHA-256 stored only, in the **same** `app.invite_tokens` table and consumed by the **same** `POST /auth/accept-invite` as every invitation (single use under concurrency, tenant and membership bound by the stored row, generic error, password policy of 12 to 128 characters). No second authentication route.                        |
| Lifetime                        | 24 h default, 1 to 72 h; expired tokens are refused and consume nothing.                                                                                                                                                                                                                                                                                 |
| Binding                         | Only an `INVITED`, identity-less user holding an active organization-scope COLLEGE_ADMIN of that tenant can be targeted; `--admin-email` disambiguates; another tenant's administrator is never selected. `created_by` is the target user (the table requires a creator and no operator account exists in a tenant).                                     |
| Retries                         | Re-issuing withdraws earlier unused tokens (one live token); revoke command; a fresh issue works after expiry.                                                                                                                                                                                                                                           |
| No second initial administrator | Refused (`ADMIN_ALREADY_ACTIVE`) once any organization-scope administrator is ACTIVE; ambiguity needs an explicit e-mail. Serialised with MFA-ticket issuance by the same per-tenant advisory lock and tenant row lock.                                                                                                                                  |
| MFA                             | `admin:mfa-ticket` only after activation, wrapping the existing `issueFirstAdminBootstrapTicket` (single use, 24 h, prior tickets revoked, closed once an administrator has a verified factor). Enrolment still requires a password step-up; before MFA every administrative route is 403.                                                               |
| Secret handling                 | Token and ticket are printed once, only when `NODE_ENV` is not production, `PLATFORM_ALLOW_LOCAL_TOKEN_OUTPUT=true` and the database host is local; otherwise the command refuses **before** issuing. Tier-3 SYSTEM audit events carry ids and expiry, never a secret; a test scans logs, audit events, token and ticket tables for every issued secret. |

Tests: `tests/integration/first-admin-onboarding.test.ts` (10) and `tests/unit/first-admin-local-output.test.ts` (3).

### Remaining limitations

- **Delivery is manual** (G4: no production invitation mailer). Printing is local-only by design, so a non-local environment cannot use these commands at all until a mailer or secure channel exists.
- **G2 unchanged**: staff invitations still carry no role.
- A sole administrator who loses both authenticator and recovery codes has no defined recovery (needs a second administrator or an operator procedure; not built).
- The CLI entry (`cli.ts`) connects to the database before it evaluates the local-only guard for the printed output; the guard still runs before anything is issued. The CLI is covered by unit and service tests, not by a process-level test.
- Platform Owner web portal: intentionally not started.
