## 2. Student identifiers

### 2.1 Model (`02` §4.4, audit class A1)

| Column | Notes |
| --- | --- |
| `id`, `organization_id`, `student_id` | composite FK `(organization_id, student_id)` → `students (organization_id, id)`; an identifier can only belong to a student of its own tenant |
| `id_type` | closed list `UNIVERSITY_PRN, APAAR, LIBRARY_CARD, HOSTEL_ID, OTHER` (`02` §4.4). `INSTITUTIONAL_EMAIL` is mentioned in §6.1 but not in the §4.4 table and is **not** accepted (open item) |
| `value` | text 1–100, trimmed (`value = btrim(value)`), stored exactly; **uniqueness is exact** (case and inner whitespace significant) because the documents define no normalisation |
| `issuer`, `valid_from`, `valid_to` | optional; `valid_to >= valid_from`; years 1900–2200 |
| `version`, `created_at`, `updated_at` | standard; `version` is the `ETag` |

`UNIQUE (organization_id, id_type, value)`. **The admission number is not an identifier**: it stays on `students` (set once, unique per organization, immutable) and cannot be expressed here (the `id_type` CHECK excludes it). Identifier endpoints never return or accept it, and a test pins that creating identifiers leaves `students.admission_number` untouched.

### 2.2 Lifecycle and immutability (database layer)

`student_id`, `id_type` and `value` are immutable: the runtime role has no `UPDATE` privilege on them, and the trigger `student_identifiers_guard` refuses any other writer (including a superuser: `23001`). `issuer`, `valid_from`, `valid_to` can change. There is **no delete** (no `DELETE`/`TRUNCATE` privilege, no route): an identifier can be end-dated, but a mistaken identifier keeps occupying its `(id_type, value)` key. This is an owner decision (§7).

### 2.3 API (mounted at `/api/v1/students`)

| Route | Permission | Notes |
| --- | --- | --- |
| `GET /:id/identifiers` | `student.profile.read_sensitive` | GRANTED for staff, SELF for the student's own; no audit on read |
| `POST /:id/identifiers` | `student.record.update` | `Idempotency-Key` required (428/400/422); body `{ idType, value, issuer?, validFrom?, validTo? }`; 201 `{ data: { id } }` |
| `PATCH /:id/identifiers/:iid` | `student.record.update` | `If-Match` with the exact version (428 missing, 400 malformed/weak, 409 stale); body `{ issuer?, validFrom?, validTo? }` (`null` clears); a no-op writes nothing and bumps no version |

Bodies are closed (`additionalProperties: false`); tenant, student, version and identity fields cannot be supplied. A duplicate `(id_type, value)` is `409 STUDENT_IDENTIFIER_EXISTS` with a neutral message (it confirms that someone holds the value, never who). At most 100 identifiers per student (`409 STUDENT_IDENTIFIER_LIMIT_REACHED`; an engineering bound, §5).

### 2.4 Authorization, audit, concurrency

- **Permissions**: `student.profile.read_sensitive` already existed (doc 10 row 24 names "IDs"). `student.record.update` is doc 10 row 27 (SENSITIVE; `DEPARTMENT_ADMIN`, `CAMPUS_ADMIN`, `COLLEGE_ADMIN`, `REGISTRAR` GRANTED), registered by `0035`, catalog and role matrix in the same change. Its only use today is identifiers; other student edits are not built. Existing tenants need `seedTenantRoles` re-run.
- **Scope**: an ORGANIZATION grant covers every student; a campus/department grant is proven from the student's ACTIVE enrolment (frozen campus/department); a student with no ACTIVE enrolment is reachable only by an ORGANIZATION grant; out of scope is the same 404 as a missing student; another tenant's student is 404. A STUDENT actor reads only their own identifiers and can never write (403 on write; row security also refuses it).
- **Row security**: forced RLS; tenant policies plus a restrictive actor policy (STAFF all; STUDENT reads own only; writes STAFF only).
- **Audit** (A1): `student_identifier.add` / `.update`, risk tier 1, subject student and placement, in the same transaction. The identifier **value is never copied into the audit event** (its `resource_id` links to the row); the cached idempotent response carries only the new id.
- **Locks**: student row `FOR NO KEY UPDATE`, then the active enrolment, then the identifier row (the guardian service's protocol). Concurrent adds of the same value: exactly one 201, the other a clean 409 (unique index). Concurrent changes with the same version: one 200, one 409.

### 2.5 UI

None. The canonical M2 UI lists a "student profile", and the web app has no student profile page (`/students` and `/profile` are placeholders), so there is no established pattern to extend.

## 3. The import framework

### 3.1 Model (`02` §4.11)

`import_jobs`: `type` (`STUDENT_RECORDS`, `EMPLOYEE_RECORDS` — names the record kind, not a role), `status` `DRAFT | VALIDATED | COMMITTED | FAILED`, `created_by`, `row_count` (1–1000), `summary` jsonb, `validation_hash`, `committed_at`, `version`. `import_job_rows`: `row_no`, `raw` (exactly as submitted), `status` `PENDING | VALID | INVALID | COMMITTED`, `normalized` (the exact proposed change), `errors`, `warnings`, and — once committed — `student_id` or `employee_id` (tenant composite foreign keys, never a loose uuid). **`file_id` and `error_report_file_id` are not created** (§7): rows arrive as JSON from the client's CSV parser (`04` line 71 puts the CSV importer in the admin client), so there is no stored file to point at, and a column nobody may write is not shipped (the rule of `0027`).

Database guarantees: forced RLS on both tables; **owner-only** restrictive policy (a job and its rows are visible and usable only to the staff user who created them, on top of the tenant boundary); `import_jobs_guard` allows only `DRAFT → DRAFT|VALIDATED|FAILED` and `VALIDATED → VALIDATED|DRAFT|COMMITTED|FAILED`, makes `COMMITTED`/`FAILED` terminal and the identity columns immutable; `import_job_rows_guard` accepts new rows only while the job is `DRAFT`, makes `raw` and the row identity immutable, and freezes the rows of a finished job ("rows immutable after commit", `01`) for every writer; CHECKs tie `VALIDATED/COMMITTED` to a hash, `COMMITTED` to `committed_at`, a `COMMITTED` row to exactly one created record, `INVALID` to at least one error; grants are `SELECT, INSERT` plus column-level `UPDATE`; no `DELETE`.

### 3.2 What a row contains (implementation choice, §7)

The documents authorize "100 students + 20 faculty" but define no columns. A row **names an existing account by its e-mail address** and carries what the existing create endpoint needs:

- `STUDENT_RECORDS`: `email, admissionNumber, admissionDate` → `POST /students` semantics (status `ADMITTED`). Optional, **matching-only** columns `name`, `dateOfBirth` (strict `YYYY-MM-DD`, real date, not in the future) and `guardianPhone` (≤ 30 characters) feed the possible-duplicate check (§3.5); they are never stored on a record. `dateOfBirth` and `guardianPhone` are SENSITIVE and are **not columns of a stored row at all**: a create request that names either is refused (400), and the client resupplies them with every validate and commit request (§3.5.4). `name` is an ordinary stored cell.
- `EMPLOYEE_RECORDS`: `email, employeeCode, employeeType (FACULTY|STAFF|ADMIN|VISITING), joiningDate` → `POST /faculty/employees` semantics (status `ACTIVE`).

The import **never creates accounts, sends invitations, enrols into programs, creates guardians, postings or role assignments.** Accounts come from the invitation flow; bulk account creation is not authorized by any document and is a separate decision.

### 3.3 Workflow and API

Mounted per record kind: `/api/v1/students/imports` and `/api/v1/faculty/imports` (doc 04 §14 lists `import` among the `/students` resources). A job of the other kind is a 404 on a mount. Every route needs `import.job.manage`.

| Route | Effect |
| --- | --- |
| `POST /` | `{ rows: [{col: text}, …] }` (1–1000 rows); `Idempotency-Key` required; stores a `DRAFT` job and its rows verbatim; a row naming `dateOfBirth` or `guardianPhone` is refused (400); 201 `{ id, version }` |
| `POST /:id/validate` | optional body `{ matching: [{ rowNo, email, dateOfBirth?, guardianPhone? }] }` (§3.5.4, never stored); evaluates every row against the current state, stores status, proposed change, errors and warnings; `VALIDATED` when no row has an error (warnings allowed), otherwise stays `DRAFT`; repeatable; `DRAFT`/`VALIDATED` jobs only |
| `GET /:id` | the job (`ETag` = version) |
| `GET /:id/rows?status&afterRowNo&limit` | the **preview**: raw values, the exact `normalized` change, errors, warnings, created record id; keyset pagination (≤100) |
| `GET /:id/error-report` | CSV download (§3.6) |
| `POST /:id/commit` | `If-Match` = the previewed job version (428/400/409), `Idempotency-Key` required, body `{ reason, acknowledgeWarnings?, matching? }` (the same `matching` as the validation it commits) |

### 3.4 Validation (non-mutating, stable)

Validation writes **only** the job's own rows and summary; a test compares counts of students, employees, users, role assignments, programs, guardians, audit events and idempotency keys around it. It is deterministic: rows are read in row order, issues are sorted (field, code, related row), messages are fixed text per code and never echo a submitted value; two validations of the same state give byte-identical rows and the same hash.

Row errors (stable codes): `REQUIRED, UNKNOWN_COLUMN, INVALID_EMAIL, INVALID_ADMISSION_NUMBER, INVALID_EMPLOYEE_CODE, INVALID_EMPLOYEE_TYPE, INVALID_DATE` (shape); `ACCOUNT_NOT_FOUND` (not in this tenant), `ACCOUNT_NOT_ACTIVE` (students), `ACCOUNT_DEACTIVATED` (employees), `ACCOUNT_HAS_STUDENT_RECORD`, `ACCOUNT_HAS_EMPLOYEE_RECORD`, `ACCOUNT_HAS_STAFF_ROLE` (students; the same predicate as `StudentService`), `ADMISSION_NUMBER_EXISTS`, `EMPLOYEE_CODE_EXISTS`, `DUPLICATE_IN_FILE` (second and later occurrence of an e-mail, admission number or employee code; `relatedRow` names the first). Shape errors added on 2026-10-22: `INVALID_NAME` (> 200 characters), `INVALID_PHONE` (> 30 characters), and `INVALID_DATE` also for `dateOfBirth`. Warnings: `FUTURE_DATE` (UTC calendar), `ACCOUNT_NOT_ACTIVATED` (invited account, employees), `ACCOUNT_SUSPENDED`, `POSSIBLE_DUPLICATE_STUDENT` (§3.5).

### 3.5 Duplicate detection (`02` §6.2; owner decisions 2026-10-22)

**Rule.** A candidate is a *possible duplicate* only when **all three** match: normalised name, date of birth, normalised guardian phone. A missing or unusable value on either side means "no match"; missing is never equal to missing. An exact admission-number conflict is not part of this rule: it stays a **hard error** (`409 CONFLICT` at admission, `ADMISSION_NUMBER_EXISTS` in an import row). A possible duplicate is a **warning**, never an error, and nothing is merged or created automatically.

**3.5.1 Data and normalisation.**

| Value | Probe (the request / import row) | Candidate (an existing student of the same tenant) |
| --- | --- | --- |
| name | `name` (optional) | `users.display_name` of the student's account (`users` has no first/middle/last columns; doc 02's split names do not exist in the schema) |
| date of birth | `dateOfBirth` (optional) | `users.date_of_birth` (migration `0036`; nullable, **no backfill**) |
| guardian phone | `guardianPhone` (optional) | phones of the student's **active** guardian links (`valid_to IS NULL`, guardian not soft-deleted) and of **legacy** contact rows (`guardian_id IS NULL`, `valid_to IS NULL`), read by `StudentGuardianService.phonesForMatching` (below) |

The candidate's date of birth is read as `to_char(date_of_birth, 'YYYY-MM-DD')`, never `::text`, so the comparison does not depend on the session `DateStyle` (a non-ISO style such as `SQL, DMY` renders `04/03/2005` and would silently disable every match; regression test in `student-duplicates.test.ts`). The probe side is strict `YYYY-MM-DD` (`parseDate`): a date has exactly one accepted spelling, so equivalent dates cannot produce different warnings or bindings.

Normalisation is the minimum: **name** = trim, then case-fold (`toUpperCase().toLowerCase()`, so "ß"/"SS" fold alike); **phone** = ASCII digits `0-9` only; **admission numbers** are never normalised. Deliberately not done: Unicode normalisation (composed and decomposed accents differ), diacritic removal, inner-whitespace collapsing, token reordering, fuzzy similarity, country-code inference, leading-zero removal, non-ASCII digit mapping. A name or phone is *usable* when it is non-empty after normalisation. Both sides use the same two functions (`normalizeName`, `normalizePhone`), applied in code after a tenant-scoped, date-of-birth-indexed read. Limitations: a person whose account name differs from the submitted name does not match; two relatives with the same name, date of birth and phone do.

**3.5.2 The shared service.** `StudentDuplicateService.find(tx, ctx, probes)` (`modules/students/student-duplicate.service.ts`) is the only implementation; the admission service and the student import adapter call it, nothing else does and no route exposes it. It is **read-only**, **tenant-scoped** (RLS plus an explicit `organization_id` filter) and **self-authorizing**: staff actor, `student.record.create` held and held at ORGANIZATION scope (the permission of the writes it guards), else 403. It does **not** require `student.guardian.read` itself: the caller never receives a guardian's phone, a date of birth or a name, only, per probe, a **fingerprint** (unkeyed SHA-256 of the tenant, the acting user, the probe's own account and the sorted candidate student ids) or `null`. The fingerprint identifies the *set* of matches *for this account and this reviewer*, so an acknowledgement cannot be reused for another account or by another administrator; the server recomputes it from the current database state and compares, so a client-supplied value alone authorizes nothing.

*What the fingerprint is, and is not (security review 2026-10-24).* It is a **freshness/binding token**, not a secret and **not an authorization boundary**. It is not opaque to its recipient: every input except the candidate ids is known to the acting user (their own id, the account they submitted, the tenant), and student ids can be enumerated by anyone holding `student.directory.list`/`search`, so such an actor can test candidate ids offline (one SHA-256 per student for a single match) and **can identify which record(s) matched**. Forging one gains nothing: the same actor obtains a valid fingerprint by submitting once without it, and it only confirms a warning they were shown. That identification reveals nothing new **only if** every holder of `student.record.create` may already read guardians and sensitive profiles at the same scope. That holds for every role of `ROLE_MATRIX` (pinned by `imports-static.test.ts`, "every role that may create students may also read guardians and sensitive profiles"); tenant roles are seeded and re-synced from that matrix and `app_runtime` cannot write `roles`/`role_permissions`, so no application path can break it. **Residual:** a privileged, out-of-band grant of `student.record.create` to a role without `student.guardian.read`/`student.profile.read_sensitive` (custom roles are not supported by the application but are not prevented by the database) would let that role confirm that a specific student has the supplied date of birth and guardian phone; review any such grant. The fingerprint is never logged (an `AppError` envelope is sent without logging), never stored raw (only inside the SHA-256 request fingerprint of a successful idempotent request) and not in audit events.

**Guardian data access.** The only code that names the guardian tables is `StudentGuardianService` (a static test pins it). The matcher therefore gets phones from `StudentGuardianService.phonesForMatching(tx, ctx, studentIds)`: internal (no route), read-only, tenant-scoped (explicit `organization_id` filter plus RLS), staff actor holding `student.record.create` at ORGANIZATION scope (re-asserted), returning `student_id -> phones` and nothing else, called only by the matcher (static test). It is not a general guardian-read path and `import.job.manage` / `student.record.create` grant no guardian-read or sensitive-profile permission (the role matrix is unchanged). The probe's own account is never a candidate. If the answer would need an unauthorized path, the rule is to stop and report; none was needed.

**3.5.3 Admission (`POST /api/v1/students`).** Smallest contract change that makes a safe acknowledgement possible: four optional body fields, all validated strictly (400): `name` (1-200), `dateOfBirth` (real past date), `guardianPhone` (1-30), `duplicateAcknowledgement` (64 hex). The first three are *matching-only*: not stored (not on `users`, not as a guardian), not in the response, the audit event or any log; the idempotency store keeps only the SHA-256 of the whole request. Flow: the record is inserted (so every hard error - exact admission number, account state, person exclusivity - wins), then the check runs **in the same transaction at the authoritative boundary**. No match, or a match equal to `duplicateAcknowledgement`: `201`. A match without or with a different acknowledgement: **`409 POSSIBLE_DUPLICATE_STUDENT`** with fixed text and `error.details = [{ field: 'duplicateAcknowledgement', message: <fingerprint> }]`; the transaction rolls back (no record, no audit event, no claim on the `Idempotency-Key`), and the client resends the same request with `duplicateAcknowledgement` set to that fingerprint after a person reviewed the warning. If the candidate set changes in between, the old fingerprint no longer matches and a new warning (new fingerprint) is returned. **Concurrency.** Hard conflicts first: the insert runs before the check, so the database-backed unique index on `(organization_id, admission_number)` (and the person-lock, exclusivity triggers and `students_org_user_uq`) still decide exact conflicts as `409 CONFLICT`. The duplicate check is a *warning under READ COMMITTED*, not a constraint: two concurrent admissions of mutual duplicates (different accounts, same name + DOB + phone) each see only committed rows, so both can pass the check and both commit unwarned; likewise an import commit does not see an admission that commits after its recheck. This is accepted (a warning, not a uniqueness rule; nothing is merged) and recorded; closing it would need a per-(tenant, DOB) advisory lock taken after the insert and before the check in every writer. A refused admission rolls back the insert, its audit event and the idempotency claim, so a retry with the right acknowledgement starts clean. The audit event of an acknowledged creation carries `metadata.duplicateAcknowledgementSupplied: true` and nothing else about the check. (`AppError` gained an optional `details`, rendered in the error envelope like validation details.)

**3.5.4 Import.** The adapter's `check` calls the service once for the whole file, in the same read-only evaluation that runs at validate **and again at commit**, so the check is rechecked under the person locks against the current state. A match adds the row warning `POSSIBLE_DUPLICATE_STUDENT` (fixed message, no field, no reference). Warnings are part of the hashed outcome: a warning that appears or disappears after the preview changes the hash, so the commit answers `409 IMPORT_PREVIEW_CHANGED` with a refreshed preview and a new job version, and an old acknowledgement cannot be used. The acknowledgement is the existing `acknowledgeWarnings: true` of the commit body *bound to the previewed job version in `If-Match`* (a stale version is `409`), verified inside the commit transaction (`409 IMPORT_WARNINGS_UNACKNOWLEDGED` otherwise) and recorded in the `import_job.commit` audit event as counts only (`acknowledgedWarnings`, `rowsWithWarnings`, `duplicateWarningRows`). The browser cannot mark a job acknowledged: no endpoint stores an acknowledgement, the server evaluates it per commit request. It is one acknowledgement for all warning kinds of the job; a candidate that is *replaced* by another with an equal warning code is not distinguishable by the reviewer (no candidate detail is ever shown) and does not change the hash.

*Within-file matches.* The same rule runs between the rows of one file (`firstEarlierMatches`, the same `usableTriple` definition, so missing never matches): in row order, a row whose triple equals an earlier row's gets one warning `POSSIBLE_DUPLICATE_IN_FILE` with `relatedRow` = the **first** row of its group. A group of *n* rows yields *n-1* warnings (rows 2 and 3 of a group of three both point at row 1, never at each other), so a pair is never reported twice and the output depends only on the stored row order (the order of the `matching` entries is irrelevant). Only rows that parsed take part. The warning carries no value and no other detail; it needs the same acknowledgement.

*Where the sensitive cells live: nowhere (resupply design, owner decision 2026-10-22).* The commit-time recheck needs `dateOfBirth` and `guardianPhone`, so the client sends them again, as a `matching` list beside the request (not as cells), with **every** validate and commit. Each entry names a stored row by `rowNo` **and** by that row's stored e-mail (compared trimmed and case-insensitively): an unknown or repeated row number, an entry with no cell, a non-text, over-long (> 40) or control-character cell is `400`; an e-mail that is not the stored row's is `409 IMPORT_MATCHING_MISMATCH` (a different or reordered file is refused instead of being matched against the wrong person). An employee import takes no matching data (`400`). The values live in request memory only: they are evaluated together with the stored, non-sensitive row and the current database state, producing the same errors, warnings and outcome hash as any validation, and are written nowhere - not to the import tables, the preview, the error report, the job, the audit event, the idempotency store or a log. No message echoes one.

Besides the HMAC binding of a committed job (below), the only persisted trace is `import_job_rows.match_presence` (0-3: bit 1 = a date of birth was supplied, bit 2 = a phone **with at least one digit**: a digit-free phone such as `---` is absent, by the same normalisation as the MAC and the matcher; an entry whose only cell is such a phone still needs a valid row binding and then contributes nothing), written by each validation and frozen with the rows when the job finishes. A commit whose resupplied cells are malformed (a non-canonical or impossible date, a future date, an over-long phone) or mistyped (a number or boolean where text is expected, a text row number) is refused with a fixed `400 VALIDATION_ERROR` before any evaluation, using the same `parseMatching` as the validation: a client error never turns a validated job into a terminal `FAILED` one, and the job, records, idempotency store and audit log are unchanged. At validate, a malformed *text* date stays row-level feedback (`INVALID_DATE`) as before; wrong JSON types are `400` on both routes, because the commit body schema leaves `matching` untyped and the service's `bindMatching` is the single validator (the HTTP layer's type coercion no longer applies to it). A commit whose resupplied **presence** differs for any row from the validated one is refused with `409 IMPORT_MATCHING_MISMATCH` *before* any evaluation, so it can neither refresh the stored preview nor slip past the acknowledgement. Equal presence with different **values** is revalidated: if the outcome (warnings included) differs from the preview, the commit refreshes the preview and answers `409 IMPORT_PREVIEW_CHANGED`, so the earlier acknowledgement is dead and a fresh one is needed for the new version; if the outcome is identical, the commit applies exactly the reviewed outcome.

*Idempotent retry of a commit (owner decision 2026-10-23: option (a), a dedicated HMAC keyring).* The commit's idempotency fingerprint covers `type, jobId, expectedVersion, reason, acknowledged` and deliberately **not** the matching values (a SHA-256 of them in the idempotency store would be guessable). The matching data is bound separately: when a commit that carries matching data succeeds, the job stores `match_binding` = HMAC-SHA-256 over `purpose \n v1 \n keyId \n tenant \n job \n canonical`, where *canonical* is, per row with any cell and ordered by row number, `[rowNo, dateOfBirth | null, phoneDigits | null]` (so it covers values, presence and the row a value belongs to; the row number is the row identity because every entry was checked against the stored row's e-mail), and `match_binding_key_label` = the active key ID of the dedicated `IMPORT_MATCHING_KEYS` ring (`docs/runbooks/secrets.md`, "Import matching-data keys"). A same-key retry that finds the stored answer recomputes the MAC of its own canonical data with the key named by the label and compares in constant time (`timingSafeEqual`): equal → the established replay (`Idempotent-Replayed: true`); different values with unchanged presence, a presence change, a moved value, or matching data on only one side → `422 IDEMPOTENCY_KEY_REUSED` (fixed text, no value, no MAC). Equivalent data is the same canonical form: phone formatting, surrounding spaces, entry order and e-mail case do not matter; any other date or digit does. **Fail closed:** without the ring, a commit (or a retry) that carries matching data answers `503 IMPORT_MATCHING_UNAVAILABLE` before anything is evaluated, locked or written; a binding whose key has been removed from the ring answers the same `503` (never a replay, never a guess); there is no downgrade to presence-only or to an unkeyed or salted digest. Commits without matching data, and employee imports, need no key. The ring is required in production (startup refuses), refuses key material shared with `CURSOR_KEYS` or `MFA_ENCRYPTION_KEYS`, and supports rotation by key ID (new bindings under the active key, verification with retiring keys; keep a retired key ≥ 24 h, the idempotency lifetime). Why not the earlier designs (threat analysis, 2026-10-23): a salted argon2id binding (drafted, removed) stores its salt beside the digest, so a reader of the table can test guesses offline; the inputs are low-entropy (a date of birth ~10^4 values, a phone ~10^9-10^10; with one known, ~10^4 guesses at the measured ~200 ms each); any keyless verifiable function of such data is a guessing oracle. The HMAC is not, as long as the key is held outside the database; **residual:** key and table together restore the oracle (runbook, "Suspected compromise"), and the MAC is deterministic per (key, tenant, job, data), which is what lets an equivalent retry be recognised but carries no information across jobs or tenants.

**Lifecycle by outcome.** create (rows stored without the two cells; a row that names them is refused) → validate/revalidate (cells used in memory; presence bits stored) → commit refused for presence (`IMPORT_MATCHING_MISMATCH`: nothing changes) → refused for a changed outcome (`IMPORT_PREVIEW_CHANGED`: refreshed preview, no values) → `IMPORT_WARNINGS_UNACKNOWLEDGED` or a write-time `IMPORT_COMMIT_CONFLICT` (rolled back) → commit-time errors (`FAILED`) → success (`COMMITTED`) → retry (as above). In every state the database holds no date of birth and no guardian phone of a row, and nothing computed from them except the presence bits and, on a committed job, the keyed HMAC binding (no unkeyed or salted digest). Request bodies and DB parameters are never logged (`logger-options.ts` records method, path and address only); the idempotency store keeps a SHA-256 of the request (rows without the two cells; for the commit, without `matching`) and the 2xx body; audit events carry counts and flags only (`matchingRowsSupplied`). **Retention (temporarily accepted, owner decision 2026-10-22):** jobs and their non-sensitive rows (e-mail, admission number and date, name, presence bits, errors, warnings) are kept indefinitely; no retention period is defined and no purge worker exists. This is a deferred production-readiness risk (§6, §7 item 16).

**3.5.5 Not done / open.** Nothing writes `users.date_of_birth` yet (no profile or account-creation path; the runtime role has no `UPDATE` privilege on the column), so in a real database the check cannot match anything until a writer and data exist (§7 item 11). `identity.dob_required` is registered in the settings registry but nothing reads it and this batch does not enforce it.

### 3.6 Error report

`GET …/error-report` returns `text/csv` (`Content-Disposition: attachment`, `Cache-Control: no-store`, `nosniff`) generated on demand from the stored rows: header `row,severity,code,field,message,related_row`, one line per error or warning. It contains **no submitted values** (messages are fixed; the only client-chosen text is a column name), and any cell a spreadsheet could read as a formula (leading `= + - @ TAB CR`) is prefixed with an apostrophe. There is no stored report file, so the "existing file/download mechanism" (the documents module: presigned upload, scan, download URL) is deliberately not used: it is built for scanned user files linked to students, and a generated, value-free CSV needs none of that.

### 3.7 Commit — the unit of work is the whole job

Documented unit: none (`01`/`02` say only `VALIDATED → COMMITTED/FAILED`, "rows immutable after commit"); `06` §2 says bulk mutations "fail the whole request (or report per-item) — never partial silent success". **Chosen: all-or-nothing in one transaction.** Order (pinned by a static test):

1. shape of the request (reason 5–500, `If-Match`, `Idempotency-Key`), then authorization: `import.job.manage` **and** the record kind's create permission (`student.record.create` / `employee.record.create`), both at ORGANIZATION scope, staff actors only (a campus/department-scoped holder is 403: students and employees have no campus before enrolment/posting, the same inert-grant rule as record creation);
2. the job row is locked `FOR UPDATE` (before the idempotency claim, so a retry waits and then replays);
3. if the job is `VALIDATED` and the version equals `If-Match`: the per-person advisory lock (`lockPersonIdentity`) of **every** account in the file, in ascending id order (one global order: no deadlock between overlapping imports; compatible with the single-record writers that take one person lock first);
4. **revalidation** of every row against the current state, then comparison with the previewed outcome (SHA-256 of the per-row status, proposed change, errors and warnings):
   - any row now invalid → nothing is created, the refreshed rows are stored, the job becomes `FAILED` (terminal), audit `import_job.fail`, `409 IMPORT_COMMIT_CONFLICT`;
   - no error but a different outcome (a warning appeared or went, a resolved account changed) → nothing is created, the refreshed preview is stored under a new version, `409 IMPORT_PREVIEW_CHANGED`: the administrator reviews and commits again with the new `If-Match`;
   - identical → proceed. (The refusals are answered *after* the transaction commits, so the refreshed state survives; they are not cached by the idempotency store, which keeps 2xx only.)
5. inside `Idempotency-Key` handling (same transaction): job must still be `VALIDATED` and at the expected version; unacknowledged warnings → `409 IMPORT_WARNINGS_UNACKNOWLEDGED`; each row is created through the **owning service's write routine** (`StudentService.insertRecord`, `EmployeeService.insertRecord`: account checks, insert, the audit event `student.record.create` / `employee.create` with the commit's reason) — the same code path as the single-record endpoints, so no rule is duplicated; rows are marked `COMMITTED` with the created record id; the job becomes `COMMITTED`; audit `import_job.commit` (tier 2, reason).
   (Step 5 also records the acknowledgement in the `import_job.commit` audit event, counts only, and step 4's recheck includes the possible-duplicate check with the resupplied matching data, after the presence check of §3.5.4; nothing sensitive is stored at any step.)
6. any 404/409 raised while creating (a concurrent writer won the admission number, the account changed state) becomes `409 IMPORT_COMMIT_CONFLICT` for the **whole job**: the transaction rolls back (no record, no audit event, no idempotency claim) and the job stays `VALIDATED`; validating again shows the cause.

Retries and duplicates: the same `Idempotency-Key` replays the stored 200 with `Idempotent-Replayed: true` and creates nothing (with matching data: only when the HMAC binding of the retry's matching data equals the stored one, otherwise `422`, §3.5.4); a new key on a finished job is `409 IMPORT_JOB_COMMITTED`; two commits of one job in parallel: exactly one applies it; two jobs wanting the same admission number or the same account: exactly one wins and the other creates **nothing at all**; job creation is idempotent the same way (same key and rows replay one job, other rows are 422).

### 3.8 Authorization and isolation summary

- `import.job.manage` (SENSITIVE, new, doc 10 row 55): `COLLEGE_ADMIN` and `REGISTRAR` only. The registrar can import students but not employees (no `employee.record.create`); the faculty mount answers 403 to a registrar. A campus-scoped REGISTRAR holds the permission but is refused at the organization-scope check.
- **Ownership**: only the creator can get, validate, preview, download or commit a job; another user of the same tenant and any user of another tenant receive the same `404 RESOURCE_NOT_FOUND` (code and message identical to a missing job). Enforced by the service (type and tenant filters) **and** by the owner-only policy of the database, which tests exercise directly.
- Account lookup is by e-mail **within the caller's tenant**: another tenant's account is `ACCOUNT_NOT_FOUND`. The importer learns whether an e-mail has an account in its own tenant; it already holds the permission to create records for such accounts.

### 3.9 UI

`/imports` ("Imports", visible with `import.job.manage`): choose the record kind (only kinds the person may create), upload or paste a CSV (parsed in the browser by a small RFC 4180 reader; the same limits as the server, fixed-wording problems that never quote the file), validate, review the preview (the exact change per row, errors and warnings in fixed wording mapped from the codes — server text is never rendered), download the error report, commit with a reason and, when needed, the warning confirmation. One `Idempotency-Key` per intent (a retry replays); the commit key is tied to the previewed version.

## 9. Rollout

`0036` is a second ordinary, additive, forward-only migration: `ALTER TABLE app.users ADD COLUMN date_of_birth date` (nullable, no default, range CHECK added `NOT VALID` so no table scan runs under the lock - the column is NULL in every existing row by construction; catalog-only, `ACCESS EXCLUSIVE` for an instant behind a 5 s `lock_timeout`), a partial index `users_org_dob_ix` (non-concurrent `SHARE` lock; empty at first), and `ALTER TABLE app.import_job_rows ADD COLUMN match_presence smallint NOT NULL DEFAULT 0 CHECK (0..3)` (constant default: catalog-only) with one column `UPDATE` grant, and `ALTER TABLE app.import_jobs ADD COLUMN match_binding bytea, ADD COLUMN match_binding_key_label text` with a validated CHECK (both NULL, or `COMMITTED` with a 32-byte MAC and a well-formed key ID; scans `app.import_jobs` under `ACCESS EXCLUSIVE`, a table created by `0035` in the same rollout) and one column `UPDATE` grant on the pair. No column holds a date of birth or phone of an import row, or an unkeyed or salted digest of one (the drafted `match_input` and the argon2id `match_binding` text column were removed before the migration was ever committed or applied). **Deploy prerequisite:** `IMPORT_MATCHING_KEYS` / `IMPORT_MATCHING_ACTIVE_KEY_ID` in the production environment (the process refuses to start without them). It is deferred behind `0019` and `0035` like every later migration (`--through`, `--dry-run` unchanged; the runner and the contract gate were not touched). No backfill, no data change, no new permission (so no extra `seedTenantRoles` run beyond the one `0035` already needs). Rollback is forward-fix only (a later migration may drop the column and index; the application treats a NULL date of birth as "cannot match"; code that sends `dateOfBirth`/`guardianPhone` needs `0036` applied first, so deploy order is migration, then application). Preflights: none beyond those of `0019`/`0035`; read-only check after applying: `SELECT count(*) FROM app.users WHERE date_of_birth IS NOT NULL` (superuser/BYPASSRLS) must be 0. Lock times on production-sized data and the effect on `app.users` writers during the `ADD COLUMN` and the (non-concurrent, table-scanning) index build are **unmeasured**; nothing was run against a production-sized table. RLS is inherited (FORCE RLS on `app.users` unchanged), the grants are unchanged (no `UPDATE` on the new column; table-wide `INSERT` since `0003` still lets the runtime role create a user row with a date of birth, which no code does), and ordering/gating are pinned by `migrate-plan`, `migrations`, `migration-contract` and `migration-0017/0019/0020` tests. Nothing was applied to any persistent database.

`0035` is deferred behind `0019` (runner contract gate; `--through` and `--dry-run` unchanged); it adds tables and permissions only, with no backfill and no change to existing rows; lock wait bounded to 5 s; lock times unmeasured on production-sized data. Existing tenants need `seedTenantRoles` re-run for `student.record.update` and `import.job.manage`. Nothing has been executed against a persistent database.

## 10. Final security review (2026-10-22) and verification notes

Findings of the review of the final diff, with what was changed:

1. **Acknowledgement binding.** Import: the acknowledgement is evaluated only inside the commit transaction after the job row lock, the exact `If-Match` version, the per-person locks and a full revalidation whose SHA-256 must equal the stored hash of the previewed outcome (which includes every row's warnings), so it is bound to the current job, the validated result and the exact warning state; no fingerprint is involved. Admission: the server recomputes the fingerprint from current data and compares. *Defect fixed:* the fingerprint did not include the account or the reviewer, so one acknowledgement could be reused for another account with the same candidates; it now binds tenant, acting user and the probe's own account (test + mutation check).
2. **Sensitive-data lifecycle.** *Superseded 2026-10-23:* the cells are no longer stored at all (resupply design, §3.5.4); no value or value-derived digest reaches any table, preview, report, audit, log or the idempotency store. Retention of the non-sensitive rows is temporarily accepted (§7 item 16).
7. **Idempotency binding (2026-10-23).** The drafted salted-argon2id binding of the matching data was rejected after a threat analysis (§3.5.4: salt stored with the digest, low-entropy inputs, offline confirmation of a guessed date of birth in minutes when the phone is known). Replaced first by a fail-closed retry, then (owner decision, option (a)) by an HMAC-SHA-256 binding under the dedicated `IMPORT_MATCHING_KEYS` ring with key versioning, constant-time comparison and fail-closed behaviour without a key (§3.5.4).
3. **Admission concurrency.** Documented in §3.5.3; exact admission-number uniqueness remains a hard, database-backed conflict that wins over the warning.
4. **Guardian access.** `phonesForMatching` is the single phone reader, internal, read-only, tenant-scoped, minimal; callers are pinned. No permission was added to any role.
5. **Migration safety.** *Change:* the range CHECK is now `NOT VALID` (a validated CHECK would scan `app.users` under `ACCESS EXCLUSIVE`). Not run against any persistent database; production lock behaviour is unmeasured.
6. **Roadmap and scope.** `docs/architecture/v3/04` is untouched (no diff); this is Milestone 2 "Organization + People" Batch 2 and no milestone is marked complete or reordered; no account-creation or invitation code was touched (`modules/users`, `0028` unchanged).

Test-database finding: three `40P01 deadlock detected` failures appeared in full integration runs in unrelated tests. They occurred only when this batch's new `student-duplicates.test.ts` and the Batch 1 test that creates and drops a trigger on `app.audit_events` (an `ACCESS EXCLUSIVE` lock on a table every file writes) ran together (2 of 6 full runs; 0 of 5 without the new file; 0 of 5 without the trigger test; 0 of 12 on reduced subsets). The new file adds audit traffic, so it raises the overlap, but the hazard is the DDL test's. That test now issues its DDL with a 150 ms `lock_timeout` and retry, so it never queues behind (or in front of) other sessions; its assertions are unchanged. After the change: 6 full runs, 0 deadlocks. The separate, previously documented `step-up.test.ts` exact-counter flake still appears (3 of 10 runs without the new file; 2 of 6 with the final code) and was not touched.
