# Secrets handling

| Rule | Mechanism |
| --- | --- |
| No secrets in git | `.gitignore` excludes `.env*` except `.env.example`; `pnpm check:secrets` + `backend/tests/security/repo-hygiene.test.ts` fail the build on secret-looking literals or env/key files; enable GitHub secret scanning + push protection on the repository |
| Development | `infrastructure/scripts/setup-dev.sh` generates `.env` with a random DB password (file mode 600) |
| CI | No secret literals in workflows. The CI database is an ephemeral service container using trust auth. Real secrets (when needed later) go in GitHub Actions encrypted secrets, scoped to environments |
| Production | Injected as environment variables from the platform secret manager; never baked into images |
| In memory | Config exposes secrets as `Secret` objects that print as `[REDACTED]`; call `.reveal()` only where the value is used |
| Logs | Pino redaction paths + request logs without headers/bodies/query strings (`logger-options.ts`, tested) |
| Errors | Config errors name the variable, never the value (tested) |
| Rotation | Any suspected leak: rotate immediately, then purge from git history |

## Cursor keys (paginated student directory)

`GET /api/v1/students/directory` pages with authenticated cursors (`backend/src/shared/pagination`). Its keys are the optional variables `CURSOR_KEYS` and `CURSOR_ACTIVE_KEY_ID`. **Both or neither** must be set: with neither, cursor configuration is absent (nothing else changes); with only one, or with an invalid value, the process refuses to start, and the error names the variable and the rule, never a value. Keys alone do **not** register the route: it also needs the separate activation setting `STUDENT_DIRECTORY_LIST_ENABLED=true` (default `false`, a plain `true`/`false`; not a secret). Setting it without valid keys also refuses to start. The setting is the operator's acceptance of the per-process rate limiter; it does not detect or guarantee a single-instance deployment.

| Topic | Rule |
| --- | --- |
| Format | `CURSOR_KEYS` is `<keyId>:<key>` entries separated by commas, no whitespace, at most 4 entries. A key ID is 1 to 16 letters, digits, `-` or `_`, starting with a letter or digit. A key is the unpadded base64url encoding of exactly 32 bytes (43 characters). `CURSOR_ACTIVE_KEY_ID` names the one key that issues new cursors; every other key only verifies. Key IDs and key material must each be unique |
| Generation | 32 cryptographically random bytes, base64url without padding, from the operator's machine or a secrets tool, for example `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"` (or `openssl rand -base64 32 \| tr '+/' '-_' \| tr -d '='`). Never derive a key from a password or a name, never reuse a key for another purpose, never type one into a ticket, chat, shell history or this repository |
| Environments | Separate keys per environment (development, test, staging, production): a cursor from one environment must never verify in another. Production keys exist only where production secrets are managed. Tests and CI generate their keys at run time and never commit one |
| Where production keys live | Injected as environment variables from the platform secret manager (see "Production" above). **The production secret-manager provider and the deployment wiring that injects these variables are not defined in this repository and require operator confirmation before the route is enabled.** Do not assume a provider |
| Lifetime | A cursor is valid for 600 seconds from issue; the verifier also tolerates an issue time up to 30 seconds ahead of its own clock (clock skew between instances). That tolerance never extends expiry |
| Rotation | (1) Generate a new key with a new ID. (2) Deploy `CURSOR_KEYS` holding the old and the new key, `CURSOR_ACTIVE_KEY_ID` still the old ID, to every instance (so every instance can verify the new key before anything issues it). (3) Switch `CURSOR_ACTIVE_KEY_ID` to the new ID and deploy. (4) Keep the old key for at least 630 seconds (600 s lifetime + 30 s skew) after the last instance switched, so cursors issued under it still verify. (5) Deploy without the old key. Cursors that outlive that window fail with the normal `400 INVALID_CURSOR`; clients restart the walk |
| Suspected compromise | A holder of a key can read the cursor contents (tenant, user, last admission number) and forge cursors for any user and filter; forging a cursor does not bypass authorization, authentication, scope or the rate limit (every page is still authorised and audited at request time), but it lets a caller jump to any position. Respond: generate a new key, make it the only key (**remove the compromised one at once, do not wait out the 630 s**), deploy to every instance, then investigate the `student.directory.list` audit events for the exposure window. All outstanding cursors fail with `400 INVALID_CURSOR`, which is the intended effect. To switch the feature off, unset `STUDENT_DIRECTORY_LIST_ENABLED` (or set it to `false`): the route is not registered. Removing the keys while the flag is still `true` makes the process refuse to start, so unset the flag first |
| Before enabling in production | Cursor keys per the rows above, **and** a single backend instance or a coordinated (shared-store) rate limiter: the directory limiter is per process (`docs/architecture/v3/21-students.md` §0c). A deployment that needs coordinated rate limiting and does not have it must leave `STUDENT_DIRECTORY_LIST_ENABLED` unset; the flag does not check this for you. Also an unanswered capacity question: one audit row per page (see doc 21 §0c, "Audit volume") |
| Logging | Request logs record the path without the query string, so a cursor never appears in a log line; audit events never contain a cursor. Do not add either to a log or metric |

## MFA encryption keys (TOTP secrets at rest)

TOTP secrets are sealed with AES-256-GCM before they reach the database (`backend/src/modules/auth/mfa/mfa-crypto.ts`, design `docs/architecture/v3/23-mfa.md` §3). The keys are the variables `MFA_ENCRYPTION_KEYS` and `MFA_ENCRYPTION_ACTIVE_KEY_ID`: **required in production** (the process refuses to start without them), both or neither elsewhere. Without them outside production, MFA enrollment and TOTP verification answer `503 MFA_UNAVAILABLE`; nothing falls back to plaintext, a built-in key or another key.

| Topic | Rule |
| --- | --- |
| Format | Same as `CURSOR_KEYS`: `<keyId>:<key>` entries, at most 4; a key is the unpadded base64url encoding of exactly 32 bytes. The key ID is stored with every factor (`secret_key_label`) and bound into the ciphertext's authenticated data |
| Separation | A dedicated key: startup refuses MFA key material that also appears in `CURSOR_KEYS`. Never reuse a database password, cookie or any other secret |
| Generation | 32 cryptographically random bytes, e.g. `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`, separately per environment; never in git, a ticket or chat |
| Where production keys live | The platform secret manager, injected as environment variables (see "Production" above). The provider and wiring are not chosen yet: this is a prerequisite of the MFA rollout (`docs/runbooks/mfa-rollout.md`) |
| Backup | Unlike cursor keys, MFA keys protect **long-lived data**: every key that still seals an ACTIVE factor must have an offline backup (sealed, two-person access) **before** the first user enrolls. Losing it locks those users out of TOTP (recovery codes still work) and forces a re-enrollment of each |
| Rotation | (1) Generate a new key with a new ID. (2) Deploy the ring with old and new key, active still the old ID, to every instance. (3) Switch `MFA_ENCRYPTION_ACTIVE_KEY_ID` to the new ID and deploy: new enrollments are sealed with it, and every existing factor is re-encrypted under it on its next successful TOTP verification. (4) Track progress (superuser, FORCE RLS): `SELECT secret_key_label, count(*) FROM app.user_mfa_factors WHERE status IN ('PENDING','ACTIVE') GROUP BY 1`. (5) Remove the old key only when that count is zero for it; factors of users who never sign in are moved by an administrative reset (they re-enroll) or the old key is kept. Removing a key early makes those factors answer `503 MFA_UNAVAILABLE` |
| Suspected compromise | A key alone reveals nothing; key **and** a copy of `app.user_mfa_factors` reveal every TOTP secret sealed with it. Generate a new key, make it active everywhere, reset (re-enroll) every factor sealed with the compromised key, then remove that key. Review `auth.mfa.challenge` audit events for the exposure window |
| Logging | Keys are `Secret` objects (print `[REDACTED]`); configuration errors name the variable and rule only; no secret, provisioning URI or recovery code is logged or audited (tested) |

## Import matching-data keys (HMAC bindings of import commits)

A student-import commit that carries resupplied matching data (date of birth, guardian phone) stores an HMAC-SHA-256 of that data on the committed job (`app.import_jobs.match_binding`, 32 bytes, with the key ID in `match_binding_key_label`), so a retry with the same `Idempotency-Key` and materially different matching data is refused (`422 IDEMPOTENCY_KEY_REUSED`) while an equivalent retry replays (`backend/src/modules/imports/import.binding.ts`, design `docs/architecture/v3/26-student-identifiers-and-imports-m2b2.md` §3.5.4). The key is what keeps the stored MAC from being an offline guessing oracle for the values: it must never be stored in the database. The variables are `IMPORT_MATCHING_KEYS` and `IMPORT_MATCHING_ACTIVE_KEY_ID`: **required in production** (the process refuses to start without them), both or neither elsewhere. Without them outside production, a commit with matching data answers `503 IMPORT_MATCHING_UNAVAILABLE` and changes nothing; nothing falls back to presence-only checks, an unkeyed digest or another key. Commits without matching data (and every employee import) do not need the key.

| Topic | Rule |
| --- | --- |
| Format | Same as `CURSOR_KEYS`: `<keyId>:<key>` entries, at most 4; a key is the unpadded base64url encoding of exactly 32 bytes; key IDs 1-16 of `[A-Za-z0-9_-]`, starting with a letter or digit. The key ID is stored with every binding and bound into the MAC input (with a purpose string, a format version, the tenant and the job) |
| Separation | A dedicated key: startup refuses import-matching key material that also appears in `CURSOR_KEYS` or `MFA_ENCRYPTION_KEYS`. Never reuse a database password, cookie or any other secret |
| Generation | 32 cryptographically random bytes, e.g. `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`, separately per environment; never in git, a ticket or chat |
| Where production keys live | The platform secret manager, injected as environment variables to every backend instance (see "Production" above); never in the database, a backup of it, or an image. The provider and wiring are not chosen yet: **a prerequisite of production rollout of import commits with matching data** |
| Lifetime of what it protects (from the code) | A binding is consulted only when a same-key retry finds the stored answer, i.e. while the commit's idempotency record is live. `IDEMPOTENCY_TTL_HOURS = 24` is a code constant (`backend/src/shared/idempotency/idempotency.ts:17`, no configuration overrides it); the claim sets `expires_at = now() + 24 h` (`:172`, or `:198` when an expired record is replaced), and a retry replays only while `expires_at > now()` (`:182`). PostgreSQL `now()` is the **transaction start time on the database clock**, and the commit sets `committed_at = now()` in the same transaction (`backend/src/modules/imports/import.service.ts` `updateJob`), so a binding can be consulted until exactly **`committed_at + IDEMPOTENCY_TTL_HOURS`**. Nothing extends a record (a replay does not touch it) and no purge exists. After that a same-key retry re-claims the key, finds the job `COMMITTED` and answers `409 IMPORT_JOB_COMMITTED` (rolled back; the binding is never read). Losing a key therefore loses only the replay of retries inside that window (they answer `503`): no backup is needed for availability. The MACs stay on the job rows (retention of import rows is an open owner decision). **If `IDEMPOTENCY_TTL_HOURS` changes, this row and the rotation rule below must be updated in the same change** |
| Rotation | (1) Generate a new key with a new ID. (2) Deploy the ring with old and new key, active still the old ID, to every instance. (3) Switch `IMPORT_MATCHING_ACTIVE_KEY_ID` to the new ID and deploy: new commits are bound with it; existing bindings are verified with the key named by their `match_binding_key_label`. (4) Wait until no process that still has the old key **active** is running (including draining requests): only such a process can create a new binding under it. (5) Retire the old key only when, on the database clock, `now() >= max(committed_at) + IDEMPOTENCY_TTL_HOURS + 1 hour` (safety margin) for the jobs bound with it - read-only check, superuser/BYPASSRLS because of FORCE RLS, **run only by an operator with approved access, never from this repository's tooling**: `SELECT coalesce(max(committed_at), '-infinity') + interval '25 hours' <= now() AS old_key_retirable FROM app.import_jobs WHERE match_binding_key_label = '<old id>'` (25 h = the current 24 h TTL + 1 h; change both together). If no job is bound with the old key the check is true at once. A wall-clock "24 h after switching" is NOT a substitute: it ignores processes still binding with the old key and clock differences between the operator and the database. (6) Deploy without the old key. Removing it early makes same-key retries of commits bound with it answer `503 IMPORT_MATCHING_UNAVAILABLE` until their window ends, then `409 IMPORT_JOB_COMMITTED` (never a replay, never a guess, never a second commit). Progress: `SELECT match_binding_key_label, count(*), max(committed_at) FROM app.import_jobs WHERE match_binding IS NOT NULL GROUP BY 1` |
| Suspected compromise | A key alone reveals nothing. Key **and** a copy of `app.import_jobs` let an attacker test guesses of the matching data of every job bound with it (the protection reduces to the low entropy of a date of birth and a phone number) and forge bindings (which grants nothing: a forged binding only decides whether a retry replays an already-stored answer). Generate a new key, make it the only key at once (do not wait out the retirement window; outstanding retries answer `503`), deploy everywhere, and treat the matching data of jobs bound with the compromised key as exposed to whoever held both. Existing MACs cannot be re-keyed (the values are not stored); they become inert once their key is gone |
| Logging | Keys are `Secret` objects (print `[REDACTED]`); configuration errors name the variable and rule only; no key, MAC or matching value appears in a response, log or audit event (tested) |
